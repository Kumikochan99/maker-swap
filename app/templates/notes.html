01

What I built and who it is for

A marketplace demo for makers

Maker Swap is a public, mobile-responsive demo of a second-hand marketplace. It is for makers and hobbyists in Singapore who want equipment for 3D printing, electronics, music, art, or workshop projects. I built it for the CognitioLabs Associate Forward Deployed Engineer assessment. It shows a complete browse, search, Q&A, and item review flow. It is not a production marketplace.

The landing page starts with a rotating hero that represents four categories. The catalogue itself has five categories. A visitor can filter it from the fixed glass navigation or from the category chips above the listings. The default view uses detailed cards. A visitor can also switch to a compact image gallery. The nav search sends its query to the same AI search panel used on the main page. It is a shortcut for someone who has scrolled down the page, not a second search system.

Each listing has a detail page with an illustrated gallery and structured specifications. Listings marked Available also have a one-screen simulated pickup checkout. The floating catalogue assistant can answer follow-up questions. Badges show whether each listing is Available, Reserved, or Sold. The core flow needs no account. The reviewer does not need to provide an AI key.

The application runs as one FastAPI service on Render. FastAPI reads the catalogue into memory and serves Jinja2 HTML. Tailwind CSS loads from its CDN. There is no React app, Node build, separate frontend deployment, or database. I chose this small stack so I could spend more of the 72 hours on search relevance, grounded answers, and the flow a reviewer can use.

02

What is seeded, simulated or limited

The catalogue is fixed demo data

  • Every listing is seeded All 16 IDs, titles, Singapore-dollar prices, categories, conditions, descriptions, specifications, tags, pickup areas, and statuses are fixed demo data in listings.json. They are not seller submissions or live stock.
  • Artwork is representative Each category has three local SVG illustrations for the main, detail, and included-material views. Listings in the same category reuse that set. This keeps the galleries self-contained, but the images are not photographs of an individual seller's item.
  • Pickup areas are display text Areas such as Jurong East and Bedok add useful browsing context. They do not identify real sellers or show precise live locations.
  • Availability is static The seed data marks 13 listings Available, two Reserved, and one Sold. Reserved and Sold items cannot open the simulated checkout. Confirming an Available item does not change its badge or catalogue record.
  • Checkout is fully simulated The detail-page dialog shows the seeded item, price, condition, and pickup area. Confirming it creates a reference number that exists only on that page. It sends no order request. It collects no address or payment details. It processes no payment and stores no reservation.
  • There is no persistent inventory A strict Pydantic schema validates the JSON catalogue when the server loads it. The catalogue then stays in server memory. Changing a listing requires editing the seed data and deploying again.
  • Conversation memory stays in one tab Q&A is stateless on the server. The current tab keeps a limited transcript in sessionStorage so it survives page navigation. This is not an account history. It does not sync across tabs, browsers, or devices.
03

Which AI tools and models were used

The app makes real model calls on the server

Coding assistance

gpt-5.6-sol max

I used Codex CLI through CognitioLabs' coding-assistance gateway while building the project. It helped me inspect the code, implement features, and run tests. The deployed app does not call this model.

Natural-language search

openai/text-embedding-3-small

The FastAPI backend uses the OpenAI Python SDK with CognitioLabs' OpenRouter-compatible gateway. It requests the openai/text-embedding-3-small model. Each listing has two cached embeddings. One contains the full structured details. The other focuses on the title, category, and discovery tags.

Every search query gets a real embedding. The app compares it with both listing embeddings using cosine similarity. Results must meet a 0.35 similarity floor. The app keeps up to the four highest-ranked matches. It also promotes exact normalized title and category phrases. This makes short searches such as a category name more reliable. Search is still based on embeddings. There is no keyword-only fallback. If the embedding call fails, the page shows an error instead of making up results.

The search API removes Reserved and Sold matches after ranking. Normal browsing still shows those records and their status badges. Filtering after ranking means a search can return fewer than four cards. This availability filter was added after the audit. It did not change the similarity scores, the 0.35 floor, or the ranking order.

The nav search is only a shortcut. It copies the query into the main search form, scrolls to that form, and submits the same backend endpoint. It does not run a second search implementation.

Catalogue Q&A

openai/gpt-4o-mini

The backend sends all 16 validated listings to the chat model as structured context. An earlier version sent only four retrieved listings. That version failed on broad catalogue questions, so I changed it to use all 16. The catalogue is small enough for this approach.

The system prompt tells the model to treat each listing as untrusted data, not as an instruction. It tells the model to use no outside facts. When the records are not enough, it must say, "I don't know based on the Maker Swap catalogue."

The model returns JSON with an answer and up to four listing IDs that it directly discussed. The server checks those IDs against the real catalogue before the browser creates links. The server checks the IDs and the response shape. It does not fact-check every sentence written by the model. Broad summaries and unknown answers do not get a generic product link.

Where the credential stays: both customer-facing AI features call the gateway only from FastAPI. The browser calls Maker Swap's own API routes. It never receives the server credential. Provider errors and timeouts appear as errors. The app does not replace a failed model call with a canned answer.
04

What was deliberately excluded, and why

I kept the project focused on finding and understanding items

Accounts and authentication

There is no login, saved profile, or real seller identity. The brief requires the core flow to be public. Account infrastructure would not improve the browse, search, or Q&A parts being reviewed.

Real payments and orders

The single-screen checkout is clearly labelled as a simulation. It is not an order system. There is no cart, payment processor, order endpoint, stored reservation, or inventory update. Real transaction work is outside the brief. I used the assessment time for search relevance and grounded Q&A instead.

Messaging and logistics

There is no buyer-seller chat, shipping quote, delivery tracking, or pickup coordination. There are no real sellers or fulfilment operations behind the seeded listings.

Database and admin tools

There is no listing editor, seller dashboard, or multi-vendor system. JSON and server memory are enough for 16 fixed records. Building admin tools would use time on work the reviewer could not test.

05

Known issues and unfinished parts

What still needs work

Resolved after the audit: search availability. Search used to return Reserved or Sold items when they ranked in the top four. For example, the Reserved Bambu Lab A1 mini appeared for "beginner setup under $150." The API now removes every Reserved and Sold match after ranking. Those items are still visible in normal browsing with their status badges. This fix did not change the embedding scores, the 0.35 threshold, or the ranking order.
  • "Art tools" can be too broad. It returns the three relevant Art & Craft listings and one Workshop Tools listing. The word "tools" creates semantic overlap. I did not lower the global similarity floor because that would bring back more unrelated results. Field weighting or simple query-intent parsing is still unfinished.
  • Price and budget words are not hard filters. Embeddings do not reliably turn words such as "cheap" or "budget-friendly" into a numeric price limit. In the audit, "portable musical instrument around $100" ranked the S$420 Roland FP-10 Digital Piano and the S$280 Yamaha Pacifica 112V Guitar ahead of the S$90 Mahogany Concert Ukulele. The ukulele was cheaper and more portable. The query "beginner setup under $150" ranked the S$420 Original Prusa MINI+ and the S$380 Bambu Lab A1 mini. The availability fix now removes the Bambu because it is Reserved. The Available Prusa can still appear even though it is over budget. Explicit price parsing and filtering are not built.
  • Condition words are not hard filters. The query "portable gear in mint condition" returned the Like new Roland FP-10 Digital Piano. It also returned three items marked Good: the Rigol DS1054Z Oscilloscope, Makita Cordless Drill Set, and Yamaha Pacifica 112V Guitar. Search uses the condition text inside the embeddings, but it does not enforce a requested condition as a filter.
  • Search tuning only reflects this catalogue. In testing, unrelated queries reached similarity scores of about 0.31. Weaker valid matches started at about 0.36. That is why the floor is 0.35. This number was chosen for these 16 records. It is not a general marketplace ranking rule.
  • The first search after a server restart is slower. Listing embeddings are cached only inside the FastAPI process. A restart clears that cache. The next search must create both embedding views for all 16 listings before later searches can reuse them.
  • Q&A cannot know facts that are not in the seed data. The listings do not provide warranties, policies, seller details, future availability, or facts outside this catalogue. The assistant should refuse those questions. That refusal is expected behavior.
  • Q&A can omit an item from a list. During the audit, the question "What items are available under S$100?" produced three correct items: the PLA Filament Colour Bundle, Mahogany Concert Ukulele, and Watercolour Studio Set. It missed the Available Raspberry Pi 4 Workbench Set at S$95. All 16 records were in the prompt. Full context reduces retrieval failures, but it does not guarantee a complete enumeration from the model.
  • Q&A can make a reasonable-sounding inference. The starter question "Which electronics item is best for a beginner?" led the model to call the Hakko FX-888D Soldering Station a great choice for beginners and user-friendly. Its listing says that it is temperature-controlled, includes three tips, and heats quickly. It does not state that the item is beginner-friendly. The server checks returned listing IDs, but it does not fact-check every sentence in the answer.
  • Mobile testing used both emulated viewports and a real phone. Automated browser checks ran at 390 px and 430 px widths. They checked page overflow, controls, labels, keyboard focus, visible focus states, image alternatives, and sampled color contrast. Separately, I tested the site multiple times throughout the build on my own physical phone using Chrome. That confirms the flow on one real device and browser, but it is not exhaustive testing across other phones, operating systems, or mobile browsers.
  • The bare cg_ prefix appears in project documentation. The audit scanned 405 local Git objects, including 231 blobs, 141 trees, 33 commit objects, and unreachable objects. It found no credential-shaped value with that prefix, no non-empty server-key assignment, and no exact .env file in a Git tree. The tracked .env.example has a comment and an empty variable assignment. It has no credential value. The bare text cg_ appears in plan.md and decisions.md because those files explain how the secret scan was done. One unreachable local Git object contains an earlier copy of the same note. None of these occurrences is an API key.
  • The flow stops before a real transaction. Checkout review and confirmation happen only in the current page. A buyer cannot contact a seller, create or retrieve an order, change a listing's status, pay, or arrange delivery. I left those parts out on purpose. This is not a production marketplace.
