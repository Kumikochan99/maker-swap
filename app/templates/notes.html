01

What was built, and for whom

A focused discovery flow for makers

Maker Swap is a public, mobile-responsive second-hand marketplace demo for makers and hobbyists in Singapore: people looking for equipment for 3D printing, electronics, music, art and workshop projects without buying everything new. It was built for the CognitioLabs Associate Forward Deployed Engineer assessment, so the goal is to demonstrate a coherent end-to-end product rather than imitate a production marketplace.

A visitor can browse all five categories, filter from either the fixed glass navigation or visible on-page category chips, and switch between the default detailed listing cards and a compact image-forward catalogue gallery. Each item opens a detail page with its own illustrated carousel and structured specifications. Visitors can also describe a need in natural language and ask follow-up questions in the floating catalogue assistant. Static availability badges distinguish available, reserved and sold seeds. The entire flow is available without an account, and the reviewer does not need to supply an AI key.

The application is one FastAPI service on Render. FastAPI reads the catalogue into memory and serves Jinja2 HTML directly; Tailwind CSS is loaded from its CDN. There is no React application, Node build, separate front-end deployment or database. That deliberately small stack left more of the 72-hour window for search relevance, grounded answers and the user-facing flow.

02

What is seeded, simulated or limited

A fixed demonstration catalogue

  • Every listing is seeded The 16 IDs, titles, Singapore-dollar prices, categories, conditions, descriptions, specifications, tags, pickup areas and statuses are authored demo data. They are not seller submissions or live stock.
  • Artwork is representative Each category uses a set of three local reusable SVG illustrations for main, detail and included-material views. They make every gallery self-contained and reliable, but they are representative artwork shared within a category, not photographs of an individual seller's item.
  • Pickup areas are display text Areas such as Jurong East or Bedok add realistic browsing context; they do not identify real sellers or expose precise live locations.
  • Availability is static The seed data marks 13 listings Available, two Reserved and one Sold. These badges do not change in the browser and are not backed by an order, reservation or inventory workflow.
  • There is no persistent inventory A strict Pydantic schema validates the JSON catalogue when it loads. It then lives in server memory, so changing a listing requires editing the seed data and redeploying.
  • Conversation memory is intentionally small Q&A is stateless on the server. A bounded transcript is kept in the current tab's session storage so it survives page navigation, but it is not an account history and does not sync across tabs, browsers or devices.
03

Which AI tools and models were used

Real model calls, made server-side

Coding assistance

gpt-5.6-sol max

Development used Codex CLI through CognitioLabs' coding-assistance gateway. It helped inspect, implement and test the project; it is not called by the deployed application.

Natural-language search

openai/text-embedding-3-small

The FastAPI backend uses the OpenAI Python SDK against CognitioLabs' OpenRouter-compatible gateway. It batches and caches two embeddings per listing: one for full structured details and one focused on title, category and discovery tags. Every submitted query is embedded by the real model, compared with both views using cosine similarity, filtered at a 0.35 relevance floor, and limited to the strongest four listings.

Exact normalized title and category phrases are promoted ahead of thresholded semantic matches so short searches such as a category name remain dependable. This is a small ranking rule layered onto model embeddings, not a keyword-only fallback: if the embedding call fails, search reports the failure instead of manufacturing results.

Catalogue Q&A

openai/gpt-4o-mini

The backend sends all 16 validated listing records to the chat model as structured context. Full context was chosen after a top-four retrieval version made broad questions fail. The system prompt tells the model to treat listings as untrusted data rather than instructions, use no outside facts, and say "I don't know based on the Maker Swap catalogue" when the records are insufficient.

The model returns a JSON answer plus up to four directly referenced listing IDs. The server validates those IDs against the real catalogue before the browser renders item links; broad summaries and unknown answers deliberately receive no generic product link.

Credential boundary: both customer-facing AI features call the gateway only from FastAPI. The browser calls Maker Swap's own API routes and never receives the server credential. Provider errors and timeouts are shown as errors; there is no canned AI-style fallback.
04

What was deliberately excluded, and why

Discovery was the product boundary

Accounts and authentication

No login, saved profile or real seller identity. Public access is part of the assessment bar, and identity infrastructure would not improve the browse, search or Q&A demonstration.

Payments and checkout

No cart, payment processor or interactive order state. Reserved and Sold are fixed seed labels only; a fake checkout or editable reservation would imply transaction capability that does not exist, while real payment work is explicitly outside the brief.

Messaging and logistics

No buyer-seller chat, shipping quote, delivery tracking or pickup coordination. There are no real sellers or fulfilment operations behind the seeded listings.

Database and admin tools

No listing editor, seller dashboard or multi-vendor system. JSON plus memory is enough for 16 fixed records and avoids spending the assessment window on operations the reviewer cannot meaningfully exercise.

05

Known issues and unfinished parts

What I would improve next

  • "Art tools" has one over-broad result. It returns the three relevant Art & Craft listings plus one Workshop Tools listing because the word "tools" creates semantic overlap. Field weighting or simple query-intent parsing was deferred rather than lowering the global relevance floor and making unrelated searches worse.
  • Budget language is approximate. Embeddings do not reliably translate words such as "cheap" or "budget-friendly" into a numeric price constraint. Explicit price parsing and filtering is unfinished, so a semantically relevant result is not guaranteed to be the cheapest match.
  • Search tuning is catalogue-specific. The 0.35 floor separated tested unrelated probes (which peaked around 0.31) from weaker valid matches (which began around 0.36), but it is an empirical boundary for these 16 records, not a general marketplace ranking system.
  • The first search after a server restart does more work. Listing embeddings are cached only in the FastAPI process, so a restart clears them and the next search must embed both listing views again before later searches can reuse the cache.
  • Q&A cannot know what the seeds do not say. It has no evidence for warranties, policies, seller details, exact availability beyond the current demo records, or facts outside the catalogue. Refusing those questions is intended behavior, not hidden completion.
  • This stops before a transaction. Browse, detail galleries, static status display, search and catalogue Q&A are implemented; contacting a seller, changing a reservation or sold status, paying and arranging delivery remain deliberately unbuilt. The demo should not be mistaken for a production marketplace.
