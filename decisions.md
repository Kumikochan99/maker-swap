# Maker Swap Decisions

- [Phase 1] Use one FastAPI/Jinja2 service on Render - minimizes tooling and deployment overhead within 72 hours.
- [Phase 1] Store the small seeded catalogue in JSON and memory - a database adds no assessment value.
- [Phase 1] Keep all AI calls and `CLASSGW_KEY` on the backend - prevents browser and repository credential exposure.
- [Phase 1] Exclude accounts, payments, logistics, and multi-vendor support - they are outside the assessment's core flow.
- [Phase 1] Treat listing location as plain pickup-area text only - avoids introducing seller identities or profile structure.
- [Phase 2] Validate seeded JSON with a strict Pydantic listing schema at load time - malformed catalogue data should fail visibly.
- [Phase 2] Use local reusable SVG category artwork instead of remote photos - keeps the deployed browse flow self-contained and reliable.
- [Phase 2] Publish a minimal truthful `/notes` page before its full Phase 5 write-up - the footer must never point to a placeholder or missing page.
- [Phase 3] Batch and cache one embedding per seeded listing, then cosine-rank exact catalogue records for each embedded query - repeat searches need one model call and cannot invent products.
- [Phase 3] Request `openai/text-embedding-3-small` because this gateway rejects the unqualified ID as unpriced; its successful response confirms the underlying `text-embedding-3-small` model.
- [Phase 3] Return the four strongest cosine matches with no arbitrary similarity cutoff - one focused desktop row avoids weak tail results, while relative ranking stays stable across query types.
- [Phase 3] Supersede the no-cutoff approach with a 0.35 cosine floor - real unrelated probes peaked at 0.31, while indirect valid matches began at 0.36, so empty results are more honest than weak forced matches.
- [Phase 3] Add truthful renovation, DIY and home-improvement tags to both workshop tools instead of lowering the global floor - improves vague relevant intent without reviving unrelated matches.
- [Phase 3] Supersede one catalogue vector with two cached views per listing (full details plus concise title/category/tags) - max-view scoring preserves detailed searches while giving specific use cases enough semantic weight.
- [Phase 3] Version the search JavaScript URL - prevents browser or Render caches from retaining obsolete interaction logic after a deploy.
- [Phase 3] Promote normalized query phrases found in category names and literal title phrase matches ahead of thresholded semantic matches - short literal queries stay reliable without weakening the 0.35 relevance floor.
- [Phase 3] Leave the known "art tools" precision issue unresolved - it returns three relevant Art & Craft listings plus one Workshop Tools listing because "tools" creates semantic overlap; field-weighted or query-parsed disambiguation was deferred to protect time for the still-unbuilt Phase 4 Q&A.
- [Phase 3] Leave budget-language handling approximate - embeddings do not reliably weight constraints such as "cheap" or "budget-friendly" against numeric prices; explicit price parsing or filtering was deferred to protect time for the still-unbuilt Phase 4 Q&A.
- [Phase 4] Put Q&A in a closed-by-default floating widget rendered by the shared base template - chat stays available on browse, detail, error, and notes pages without restructuring the server-rendered layouts.
- [Phase 4] Keep Q&A stateless on the server and persist a bounded transcript in `sessionStorage` - conversation survives full-page navigation within one tab without accounts, a database, or indefinite browser storage.
- [Phase 4] Initially give gpt-4o-mini only the top four Phase 3 retrieval matches as structured context - this kept prompts small and citations specific, but made broad catalogue questions fail when no listing cleared the similarity floor.
- [Phase 4] Supersede filtered Q&A retrieval with all 16 validated listings in every prompt - the fixed catalogue is small enough for complete context, so broad questions no longer depend on an arbitrary similarity match.
- [Phase 4] Treat “what products are in here”, “what do you sell”, and “what’s available” as requests to summarize the current listings, not as requests for an unstated stock guarantee - keeps broad answers grounded without a false “I don’t know”.
- [Phase 4] Fix the full-context linking regression by having gpt-4o-mini return up to four directly referenced listing IDs and validating them server-side - specific answers regain item links, while broad and unknown answers avoid a misleading generic catalogue link.
- [Phase 4] Surface AI-provider failures as explicit widget errors with no canned answer - preserves the assessment's real-AI requirement when a model call fails.
- [Phase 1] Exclude the supplied assessment PDF from Git history - it is reference material, not public application source.
- [Phase 5] Structure `/notes` around the brief's five required questions and document the effective, superseding Phase 3 and Phase 4 designs - reviewers should not have to reconstruct the final behavior from the development history.
- [Phase 5] Name the two accepted search precision issues, in-memory embedding cache, session-only Q&A history, seeded catalogue boundaries and deliberately excluded transaction scope - the assessment should present limitations as plainly as completed features.
- [Phase 6] Add collected headless-browser regressions for catalogue-anchor scroll position, full-catalogue restoration after clearing search, and direct Q&A citation links; expand literal category-name cases across all five categories - these past bugs affect usability, answer coherence and scope/execution, while markup-only assertions did not protect the JavaScript behavior.
- [Phase 6] Verify the live reviewer journey in one fresh non-persistent browser context, then check 390 px and 430 px layouts plus labels, keyboard focus, Escape behavior, image alternatives and sampled contrast - the deployed browse, search, grounded/unknown Q&A, detail and `/notes` flow passed without a graded product defect to fix.
- [Phase 6] Leave two passing-suite deprecation warnings from Starlette's TestClient dependencies unresolved - they are third-party migration notices with no user-facing or assessment-criteria impact, so dependency churn is not justified inside the demo window.
- [Phase 6] Leave the bare `cg_` text in `plan.md` unchanged - it is an instruction to search for the gateway-key prefix, not credential material. A scan of the full local Git object database, including unreachable objects, found no credential-shaped value and no tree containing an exact `.env` path; rewriting history would add risk without improving a graded criterion.
- [Post-Phase 6 polish] Replace the duplicate header and browse-page category controls with one fixed, warm glass navigation menu - the Maker Swap brand and the visually distinct All Listings entry both return to the full catalogue, while one category control reduces navigation ambiguity. Keep Workshop Tools as a fifth menu item in addition to the four named polish examples because it is a real catalogue category and removing its only filter would make those listings harder to reach.
- [Post-Phase 6 polish] Expand the honest footer with a short assessment description plus working catalogue, build-notes, source-repository and GitHub-profile links - no email address, placeholder contact detail or dead destination is invented for the demo.
- [Post-Phase 6 polish] Extend each validated listing with two-to-four gallery image paths and two-to-six structured specification rows, then seed three of each for all 16 records - richer detail pages and AI context are worthwhile without adding a database or seller-editing workflow.
- [Post-Phase 6 polish] Reuse three locally hosted SVG views per category across listing galleries - this keeps the demo self-contained and gives the gallery meaningful main/detail/material views, while `/notes` and the detail page explicitly state that the artwork is representative rather than item photography.
- [Post-Phase 6 polish] Seed 13 Available, two Reserved and one Sold listing; render the status on browse/search cards and detail pages, and include it in both embedding and Q&amp;A context - the labels are static JSON facts, not interactive inventory, and the model is instructed never to call Reserved or Sold items available to buy.
- [Post-Phase 6 browse views] Keep the existing detailed listing-card layout as the default and add a client-side Gallery toggle that restyles the same rendered records - there is no duplicate catalogue state, category-filtered and AI-search results both switch instantly, and a session-only preference preserves the selected view across category reloads without changing a first-time visitor's default.
- [Post-Phase 6 browse views] Use two square, image-forward columns at narrow widths, then three, four and five columns as space increases; hide description, category and pickup only in Gallery view while retaining title, price and condition. Keep Reserved and Sold over the image with their existing high-contrast colors and slightly tighter badge spacing so status remains explicit on compact tiles.
- [Post-Phase 6 browse filters] Supersede the earlier single-category-control choice by restoring the browse-page filter chips alongside the glass-nav dropdown - the preferred experience combines quick nav-level access from anywhere with visible, in-context filtering above the catalogue. Both controls use the same category query, expose the same active state, and preserve the catalogue anchor in List and Gallery views.
- [Post-Phase 6 landing polish] Add a seven-second, auto-advancing carousel featuring one available listing from each of the four requested categories, with hover and keyboard-focus pausing plus direct previous/next controls - this is optional landing-page polish rather than work tied to a specific assessment rubric criterion.
- [Post-Phase 6 landing polish] Supersede the separate featured shelf with a single dominant hero carousel: the original landing copy appears directly over the unscrimmed first listing illustration, while slides two-to-four separate their product facts from the artwork. Keep real seven-second rotation even for reduced-motion preferences (the existing CSS removes the animated transition), and retain hover/focus pausing and manual arrows.
- [Post-Phase 6 simulated checkout] Add one client-only review dialog to Available listing details, showing the seeded title, condition, price and local pickup area before a single confirmation produces a six-digit page-only reference. Do not render the trigger or dialog for Reserved or Sold seeds, and do not call an API, collect forms or mutate catalogue state; the interaction is explicit product-flow simulation while implementation effort remains concentrated on real search relevance and grounded Q&amp;A.
